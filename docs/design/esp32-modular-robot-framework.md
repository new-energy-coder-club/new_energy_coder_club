# NEC-EMF：ESP32 机器人嵌入式模块化框架 · 重构方案

> 版本：v1.0 草案（2026-09-17）｜ 状态：待评审（Maintainers 周会）
> 定位：以 ESP32 为主控、ESP32 系芯片为子控制器（电调/视觉/传感）的机器人嵌入式端模块化框架
> 叙事挂靠：ESP32-C3/C6/H2 为 **RISC-V 内核**，本框架是社区 RISC-V × AI 主线在"控制域"的落地（与 K230"感知域"互补）

---

## 1. 背景与动机

### 1.1 现状：仓内嵌入式资产的"碎片化"

| 已有资产 | 形态 | 问题 |
|---|---|---|
| 机器狗 ESP32-S3 人脸/颜色识别工程 | 完整 Arduino 工程，任务注册 + 队列 + IIC 从机寄存器协议（0x52） | 各自为政；颜色工程缺文件；协议映射不一致（红/绿寄存器 README 自述"可能不一致"） |
| CURC2026 M3508 工程（STM32H723 + C620 电调） | 完整 CubeMX 工程，`bsp_fdcan → dm_motor_drv → dm_motor_ctrl` 三层驱动 | 宿主是 STM32 而非 ESP32；无 RTOS；无 README |
| HCX-A ESP32-S3 驱动板（重邮开源套件） | 有调试日志与外部 BoardA 模块库 | 代码未入库 |
| hicar-pi5：Pi5 主控 + ESP32-S3 驱动板 | 架构设计文档 | 纯文档无代码 |
| unitree M8010（RS485）/ DM4310 MIT 模式 / 520 电机选型 | 方案决策记录 | 驱动代码均未入库 |
| `embedded_project_template/` | 330 行 README 模板 | 无代码骨架 |

**核心矛盾**：社区不缺"调通过的单点"，缺的是**统一的模块化框架**——每个赛季都在重新造电调通信、重新约定寄存器表。这正是 README 里"BSP 乐高"哲学（README.md L53-57）尚未兑现的部分。

### 1.2 目标

一套框架，三种角色，一条总线契约：

```
┌─────────────────────────────────────────────────────────┐
│  上位机（可选）：K230 / 树莓派5（openEuler）/ Micro-ROS    │
└──────────────────────┬──────────────────────────────────┘
                       │ UART / UDP / 星闪SLE（遥操作）
┌──────────────────────┴──────────────────────────────────┐
│  主控节点 NEC-EMF Host：ESP32-S3                          │
│  决策调度 · 总线仲裁 · 遥测上报 · 状态机                    │
└──┬───────────┬───────────┬───────────┬──────────────────┘
   │CAN(TWAI)  │CAN(TWAI)  │I2C(0x5x)  │RS485
┌──┴───┐   ┌───┴───┐   ┌───┴────┐  ┌───┴─────┐
│电调节点│   │电调节点 │   │视觉节点 │  │执行器节点 │
│ESP32-C3│   │ESP32-C3│   │ESP32-S3│  │unitree   │
│+M3508 │   │+DM4310 │   │(已存在)│  │M8010     │
└──────┘   └───────┘   └────────┘  └─────────┘
 RISC-V      RISC-V      已跑通      方案已定
```

**为什么电调子控用 ESP32-C3/C6 而不是继续 STM32**：RISC-V 叙事一致（C3/C6 是 RISC-V）、单芯片集成 TWAI（CAN）控制器、成本低、ESP-IDF 统一工具链、且 Micro-ROS 有官方 ESP32 支持——与 ROS 2 视觉栈（OSPP 课题 #2）天然衔接。

## 2. 框架架构设计

### 2.1 固件分层（沿用已验证的 M3508 三层范式）

```
app/        应用层：机器人行为（底盘/机械臂/云台状态机）
ctrl/       控制层：PID、速度/位置环、运动学解算        ← 参考 dm_motor_ctrl.c
drv/        驱动层：电调协议（C620/DM/舵机/RS485执行器） ← 参考 dm_motor_drv.c
bsp/        板级层：TWAI/I2C/RS485/GPIO/MCPWM 抽象      ← 参考 bsp_fdcan.c
protocol/   契约层：总线报文 ID 分配表 + 寄存器/邮箱定义（头文件唯一真相源）
```

**关键决策**：`protocol/` 独立成层且**以头文件/表格为唯一真相源**（single source of truth），主控与所有子控包含同一份契约——根治目前"两个视觉工程寄存器映射不一致"的问题。

### 2.2 总线契约：NEC-Link

| 通道 | 用途 | 契约 |
|---|---|---|
| **CAN (TWAI) 1Mbps** | 主控 ↔ 电调节点（骨干） | 兼容 C620 现有 ID 布局：0x200 控 ID1-4 / 0x1FF 控 ID5-8，反馈 0x201-0x208；扩展段 0x300+ 用于 ESP32 电调节点的状态/参数帧（可直接复用 M3508 驱动逻辑） |
| **I2C 寄存器式** | 主控 ↔ 视觉/传感节点 | 沿用现有 0x52 从机模式，地址段规划：0x50-0x5F 视觉 / 0x60-0x6F 传感；寄存器表统一进 `protocol/nec_i2c_reg.h` |
| **RS485** | 主控 ↔ unitree M8010 执行器 | unitree_actuator_sdk 原生协议（人机/双足场景） |
| **UART 115200** | 调试与日志（现状惯例） | 统一 `LOGx()` 宏 |
| **星闪 SLE / ESP-NOW** | 遥操作链路 | 星闪手柄（WS63）→ 主控；ESP-NOW 作备份链路 |

### 2.3 节点固件模板（每个子控 = 同一骨架）

每个节点固件固定为已验证的"任务注册"模式（来自 esp32 视觉工程）：

```
node_xxx/
├── README.md            # 模块契约卡片（套用 embedded_project_template）
├── node_config.h        # 节点 ID、总线地址、引脚（唯一需要改的文件）
├── main/
│   ├── app_main.c       # 仅做 register_xxx() 任务注册
│   ├── task_sense.c     # 采样/解算任务 → 队列
│   └── task_report.c    # 总线上报任务 ← 队列
└── test/                # host 侧单元测试（协议编解码）
```

## 4. Vibe Coding 工作流（AI 辅助开发约定）

框架按"AI 友好 = 小上下文 + 强契约"原则设计，让 AI Agent 可靠地产出可合并代码：

1. **AGENTS.md 作为架构宪法**：框架根目录声明——分层依赖方向（app→ctrl→drv→bsp，禁止反向）、契约唯一真相源在 `protocol/`、所有新节点必须含 README 契约卡片与 test/、提交规范（Conventional Commits + `node(xxx):` scope）。
2. **每个模块一个 Spec 卡片**：README 固定五段式（职责/接口/配置/验收/参考），AI 生成代码前先读卡片——卡片即 prompt，杜绝"凭印象写驱动"。
3. **小步 PR 流**：每个节点/驱动一个 PR；AI 任务分解粒度 = "一个寄存器表 + 一个编解码函数 + 一组测试"。
4. **测试即护栏**：协议编解码必须 host 侧可测（不依赖硬件，Python/C 皆可）；HIL（硬件在环）测试记录进 docs/；CI 跑 markdownlint + 协议头文件一致性检查（脚本校验 ID 不冲突）。
5. **AI 结对场景白名单**（从简单到难）：补节点 README → 写协议编解码+测试 → 移植驱动（给参考实现）→ 新节点骨架。每场景在 `docs/prompts/` 沉淀一条验证过的 prompt 模板。

> 注：仓库当前无任何 AGENTS.md/AI 配置，本框架是建立该约定的试点，成熟后上收到仓库根。

## 5. 验证策略

| 层级 | 方法 | 门槛 |
|---|---|---|
| 协议编解码 | host 单元测试（电脑直接跑） | CI 必过 |
| 单节点 | 开发板 + 电机空转（电流环限流 2A 内，参考 M3508 诊断 main.c 的保守值） | 实验室 A416 实测 |
| 总线集成 | 主控 + 2 电调节点 + 1 视觉节点同跑 30min 无帧丢失 | 帧错误计数=0 |
| 整机闭环 | 星闪手柄 → 主控 → 电调 → 底盘 | 遥操作演示视频 |

| 时间 | 里程碑 |

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| ESP32-C3 单核算力限制电调控制频率 | 电调节点只跑电流/速度环（≤10kHz PWM 足够），位置环放主控；必要时节点升级 ESP32-C6 |
| 团队 ESP-IDF 经验少于 Arduino | 节点骨架同时提供 ESP-IDF 版与 Arduino-as-component 版；R2 先用 Arduino 降低门槛 |
| esp-who 闭源组件依赖 | 视觉节点只保留接口层，模型组件以 ESP-IDF 组件管理器声明式拉取，不入库（与 NOTICE 策略一致） |
| 与 STM32 存量赛季工程冲突 | 框架不替代赛季 STM32 工程，协议层保持 C620 ID 兼容，可混合组网 |
